### ★最大の発見 ── NK-08 は実質「北海道だけの問題」

複数の系にまたがる都道府県は4つある。**しかし、分かれ目が陸上にあるのは北海道だけだった。**

| 都道府県 | 系 | 分かれ目の場所 | 道路がまたぐか |
|---|---|---|---|
| **北海道** | XI・XII・XIII | ★**陸上**（市・振興局の境） | ★**またぐ** |
| 東京都 | IX・XIV・XVIII・XIX | 海上（小笠原・沖ノ鳥島・南鳥島） | ✗ |
| 鹿児島県 | I・II | 海上（I系は奄美群島・トカラ列島等の**島嶼のみ**。本土は II系） | ✗ |
| 沖縄県 | XV・XVI・XVII | 海上（本島 / 宮古・八重山 / 大東諸島） | ✗ |

- 東京都: IX系以外はすべて北緯28度以南の島。★**伊豆大島は北緯28度より北なので IX系。**
- 鹿児島県: I系は「北緯32度〜27度、東経128度18分〜130度の区域内にある**すべての島**」。
  鹿児島市（東経130度33分）も種子島（東経130度59分）も東経130度より東で区域外＝II系。
- 沖縄県: 経度だけで3つに分かれるが、いずれも別の島。

★★**したがって「系の境界をまたぐ道路」の扱い（NK-08）は、北海道でしか起きない。**

### 実装

`preprocess/src/kansui/crs.py`。★**地理空間ライブラリに依存しない**ので、
geopandas を入れずに単体テストできる。

```python
zone_of(Place(pref_code="14", municipality="藤沢市")) == 9
epsg_for(Place(pref_code="14", municipality="藤沢市")) == 6677   # ★藤沢版と同じ
```

| 設計判断 | 理由 |
|---|---|
| 適用区域の文言を**告示のままコメントに写す** | 要約すると告示に突き合わせられなくなる |
| 決められないときは **`ZoneUnknownError`** を投げる | ★既定値（XII系など）に丸めない（絶対ルール10） |
| `pref_code` は**半角2桁の文字列**必須 | ★`"01"` を `int` で渡させない。T-16（YAML の 0 始まりが8進数）と同じ事故を型で止める |
| 検査に **`\d` を使わない** | Python の `\d` は**全角数字（１４）にも一致する**（藤沢版 T-16） |
| 振興局名は**頭の「北海道」だけ**外す | 告示は「北海道後志総合振興局」、N03 の `N03_002` は「後志総合振興局」。★他の言い換えは許さない |
| 度分秒を `_dms(130, 13)` の形で書く | 10進度の数値だけ置くと告示と突き合わせられない |

## P-4 国土地理院ベクトルタイルの幅員区分 ✅

**問い**: 全国で取れる `vt_rnkwidth`（幅員区分）は、PLATEAU の実測幅員の代わりになるか。

### 結論

| | |
|---|---|
| **順序としては使える。採用する** | 無作為な2本の大小一致 **93.7%**（OSM 道路種別は 85.9%）。PLATEAU の無い地域の手段として**明確に上** |
| ★**絶対値の閾値には使わない** | 実測値が区分の範囲に入るのは **51.6%** だけ。しかも**片側に偏る** |
| ★**採否の前提** | 最適化ベクトルタイルは**試験公開**。「URL やデータ構成、属性の有無や名称等が変わる可能性があります」と国土地理院が明記している |

### 一次情報

| | |
|---|---|
| 属性仕様書 | https://maps.gsi.go.jp/help/pdf/vector/optbv_attribute.pdf |
| 更新履歴の最終 | **令和7年11月21日**（注記の文字グループ属性の追加） |
| ★過去の改正 | 令和4年11月25日に「**`vt_rnkwidth` の属性名・属性値**に誤りがあったため修正」。★属性が書き換わった実績がある |
| 取得日 | 2026年9月20日 |

仕様書の記載（原文）:

- `vt_rnkwidth`（ズームレベル 11〜17）文字型 ── 値は
  **3m未満 / 3m-5.5m未満 / 5.5m-13m未満 / 13m-19.5m未満 / 19.5m以上 / その他 / 不明**
- `vt_width`（ZL 14〜17）数値型 ── 「**地図表示用の仮想的な幅員**」★実測ではない。**使わない**
- `vt_lvorder`（ZL 11〜17）数値型 0〜4 ── 「階層順」

★★**`vt_rnkwidth` が「何の幅」なのかは仕様書に書かれていない。**
車道の幅か、歩道・路肩を含む道路区域の幅かの記載が無い。
→ **下の食い違いが「ずれ」なのか「測っているものが違う」のかは、この比較だけでは決められない。**

### ★復号が正しいことの確認

MVT のタイル内ローカル座標を経緯度に直すとき、**上下が反転していてもタイルの範囲内には収まる**ので
bbox 検査では気づけない。OSM の道路網と重ねて直接確かめた。

> RdCL から最も近い OSM 道路までの距離: **中央値 0.00m / p90 0.37m / 最大 8.35m**

★**地理院 RdCL と OSM の道路中心線はサブメートルで一致する。** 属性の載せ替えは安心して行える。

### 結果

| 区分 | 区分の範囲 | n | 実測中央値 | IQR | 範囲内 |
|---|---:|---:|---:|---:|---:|
| 3m未満 | 〜3.0 | 1,085 | **3.94** | 0.76 | 15.0% |
| 3m-5.5m未満 | 3.0〜5.5 | 9,010 | **5.51** | 1.83 | 49.1% |
| 5.5m-13m未満 | 5.5〜13.0 | 2,207 | **11.97** | 6.33 | 64.8% |
| 13m-19.5m未満 | 13.0〜19.5 | 227 | **17.95** | 3.37 | 67.4% |
| 19.5m以上 | 19.5〜 | 753 | **25.09** | 0.87 | 90.6% |

- ★**中央値は単調に増える**（3.94 < 5.51 < 11.97 < 17.95 < 25.09）
- ★**絶対値は合わない。** 範囲内は全体で **51.6%**。1段階のずれまで許せば 98.0%
- ★★**ずれは片側に偏る**: 実測のほうが**広い 47.2%** / 狭い **1.2%**（39:1）。
  → **偶然のばらつきではない。** PLATEAU が測っているのは**道路区域の幅（歩道・路肩込み）**なので、
  地理院の区分はそれより狭い何かを指していると考えると辻褄が合う。
  ★ただし**仕様書に定義が無いので、これは推測である。断定しない。**

### ★決め手: OSM 道路種別の近似より良いか

PLATEAU の無い地域での代替は「何も無い」ではなく「**OSM 道路種別からの近似**」（藤沢版の市域外と同じ）。
そちらと比べる。

| | 地理院の幅員区分 | OSM の道路種別 |
|---|---:|---:|
| **無作為な2本の大小一致** | **93.7%** | 85.9% |
| Spearman ρ（実測幅員との） | **0.741** | 0.694 |

区分の中の散らばり（実測幅員の四分位範囲）でも差が出る:

| 地理院 | IQR | | OSM | IQR |
|---|---:|---|---|---:|
| 19.5m以上 | **0.87m** | | primary | **10.07m** |
| 3m未満 | **0.76m** | | residential | 1.87m |
| 13m-19.5m未満 | 3.37m | | trunk | 3.62m |

★**OSM の `primary` は IQR が 10.07m あり、幅についてほとんど何も言っていない。**
地理院の「19.5m以上」は IQR 0.87m。**区分のほうが道幅をよく表している。**

### ★このパイロットで見つかった設計上の宿題

★★**PLATEAU のある都市と無い地域で、幅の出所が変わる。**
両者は系統的にずれている（実測のほうが広い側に 47.2%）ので、混ぜると
**市境をまたいだ瞬間に `μ·narrow(e)` の効き方が変わり、不自然な迂回が出る。**

選択肢:

| | 内容 | 評価 |
|---|---|---|
| (a) | **全国で地理院の区分に統一** | ★一様。粗いが破綻しない |
| (b) | PLATEAU があれば実測、無ければ区分 | 細かいが**地域で挙動が変わる** |
| (c) | 経路計算は区分に統一し、実測値は表示だけに使う | 一様さと情報量を両立 |

→ ★**2026-09-20、利用者が (c) を選択。決定。**
**経路計算は地理院の区分に統一し、PLATEAU の実測値は表示だけに使う。**
経路の選好では**精度より一様さ**が効くため。`config.yaml` の `width:` に記録した。

★あわせて: 藤沢版の `routing.width_narrow_at_m = 4.0`（建築基準法42条2項道路の区切り）のような
**絶対値の閾値に区分を当ててはいけない。** 「3m未満」とされた 1,085本の実測中央値は **3.94m** で、
4m の線を引くと大量に取りこぼす。K-10（消防車の最低幅）も同じ理由で区分では答えられない。

## P-5 先行確認: 立体交差は地理院タイルだけで拾えるか（★本番ではない）

P-4 のために取ったタイルで、ついでに確かめた。**適合率は測っていない**（下記）。

藤沢版の公式「冠水注意箇所」13件は**すべて立体交差**である。

| 手がかり | 拾えた件数 |
|---|---:|
| ① 道路が `vt_code` 2704/2714（トンネル） | **8/13** ── すべて「◯◯**地下道**」 |
| ② 交差する鉄道が `vt_railstate`「橋・高架」または `vt_lvorder` ≥ 1 | **4/13** ── すべて「**高架下**」「アンダー」 |
| **①＋②** | ★**12/13（92%）** |

★★**①と②は重ならない。** 地下道と高架下は別の現象で、別の手がかりでしか見えない。
**片方だけを実装すると、もう片方を丸ごと落とす。**

拾えなかった1件は **西富地下道**。近くに `2703`（道路の橋・高架）はあるが、
鉄道が無く道路トンネルの印も無い。★道路どうしの立体交差は、この2つの手がかりでは拾えない。

参考: 無作為に選んだ市内の道 3,000本で同じ条件が立つ率は **1.70%**。
★**これは適合率ではない。**「条件が簡単に立ってしまうか」の下限を見ただけである。
適合率は P-5 本番で候補を無作為抽出して目視照合する（藤沢版 V-2 と同じやり方）。

### OSM のタグとの関係（市域内・縁から200m内側 37,615本）

## P-5 アンダーパスの幾何推定 ✅（★適合率は未測定）

### ★測ったこと・測っていないこと

| 長 | **−49%** | 30 → 17 | 25.2 → 16.8MB |

市域+3km ならグラフ全体がメモリに載るので困らなかった。
→ ★**全国版では A\* が必須。** 「経路に要る区画だけ読む」設計では、

## ★NK-19 の解決と、そこから生じた制約（2026-09-21）

国土地理院に照会した結果（★利用者ご本人が問い合わせ）:

| 問い | 回答 |
|---|---|
| 標高タイルは「基本測量成果」に該当するか | ★**該当する** |
| 加工した経路データの一般公開に承認が要るか | ★**原則として測量法第30条（使用）の承認申請が必要** |
| 例外① | 一般公開せず、自分の PC 内や組織の内部作業でのみ利用する場合 |
| 例外② | 標高値の解析や加工データを生成・配布せず、配信サーバーからタイルを読み込んで**そのまま表示するだけ**の場合 |

★**このアプリはどちらの例外にも当たらない**（Δh を計算し、加工データを生成し、配布している）。
→ **第30条の承認申請へ。**

### ★★申請フォームで判明した決定的な制約

申請画面の注記:

> **簡便な方法により国土地理院の測量成果を復元できる場合は、承認することは出来ません。**

つまり「審査が重くなる」ではなく **承認されない**。

★**藤沢版の配布物はこれに抵触していた。**

| | |
|---|---|
| `graph.bin` の `nodeElev` | 標高値そのもの（0.1m 単位の Int16）を**ノード 160,880点** |
| `graph.json` | ★**offset・型・長さを公開していた** |
| 結果 | → `Int16Array` として読めば**標高値がそのまま取り出せた** |

### 対応（2026-09-21）

★**配布物から `nodeElev` を外した。** 残る地理院由来のデータは `edgeScore` のみ。

```
S_topo = √( exp(−Δh₁₀₀/d) · exp(−Δh₂₅₀/d) )  → 0〜254 に量子化
```

- Δh は「その点と**近傍最小との差**」であって標高値ではない
- 2半径の**幾何平均**を取り、さらに **255段階に量子化**
- → ★**絶対標高には戻せない。「復元できない」が正しくなる。**

| | 藤沢版 |
|---|---|
| `graph.bin` | 4.63MB → **4.31MB** |
| gzip | 2.12MB → **1.93MB** |
| ★失ったもの | **F-03 ルート標高プロファイル**。★要件定義書では「**必須・本アプリの差別化機能**」だった |
| 冠水リスクの表示 | ★**影響なし**（S_topo は残る） |

### ★全国版への制約（NK-20）

`config.yaml` に `dem.distribute_node_elevation: false` として記録した。
**★true にしないこと。復活させるなら承認を取り直すこと。**

★**NK-21 を起票**: 承認が下りるまで、藤沢版の限定公開を続けてよいか。
パスコードは `CLAUDE.md` に自ら「access control ではない」と記録しているので、
例外①（一般公開せず内部利用のみ）に当たると言い切るのは苦しい。
→ **同じ窓口に併せて照会する**（★利用者ご本人の作業）。

## クライアント実装 ── ★踏んだ罠2つ（2026-09-21）

### ★罠① ワーカーからの相対パスは `/assets/` に解決される

### ★何が起きていたのか（instrument して初めて分かった）

## ★実機で初めて出たバグ ── `hidden` が CSS に上書きされていた（2026-09-21）

利用者から「**『理解しました』をタップしても免責が閉じない**」と報告。

### 原因

```css
.modal { position: fixed; inset: 0; display: grid; ... }
```

`[hidden]` は**UA スタイルの `display: none`** でしかない。
こちらで `display: grid` と書くと**上書きされ、`hidden = true` にしても閉じない。**
モーダルが画面全体を覆ったまま、何も操作できない状態だった。

→ 対策: `[hidden] { display: none !important; }`

### ★★なぜ開発機で気づけなかったか（これが本題）

**合成イベントを要素へ直接送っていたため、重なった要素の当たり判定を素通りしていた。**

```js
cv.dispatchEvent(new MouseEvent('click', {...}))   // ← 地図の canvas へ直接
```

★この送り方では、**上に何が乗っていようと**ハンドラが動く。
だから「モーダルが全面を覆っている」ことに**最後まで気づけなかった。**
しかも `disclaimer.hidden === true` は**真を返す**（属性は立っている）ので、
DOM を見ても正常に見えた。

★スクリーンショットも助けにならなかった（タブが背面で真っ黒だった）。

### ★これからの確かめ方

**`document.elementFromPoint()` で「その座標に実際にあるもの」を見る。**

```js
document.elementFromPoint(x, y).id   // 閉じる前: "disclaimer" / 閉じた後: "maplibregl-canvas"
```

★ボタンも**座標から引いた要素**を押す（`elementFromPoint(...).click()`）。
これなら重なりを素通りしない。

★**合成イベントで動いた ≠ 利用者が操作できる。** 今回はこの差がそのまま出た。

## ★NK-06 の性能要件を決めた（2026-09-21・利用者判断「距離帯ごと」）

### まず、要件を決める前に見つかった3つの誤り

| | 何が起きていたか | 影響 |
|---|---|---|
| ★**同じ区画を2回読む** | 短距離は起点と終点が同じ区画になり、`ensure([c, c])` が重複を落としていなかった | 確定ノード **+38%** / 通信量 **+44%**。★例外は出ず**経路も所要も正しく見える** |
| ★**費用0のリンク** | `rint(t*10)` が 0 に丸まるエッジが 1,351本 | **ただで通れる道**になっていた |
| ★**許容的でないヒューリスティック** | 量子化後の最高速度が 149km/h なのに、直書きの 100km/h を使っていた | **最短経路である保証が崩れていた** |

★★**`verify_mesh_merge.py` では1つ目を見つけられない。** あれは Python の写しで、
区画を**重複なく**回すため、クライアントだけにある誤りは原理的に出ない。
→ **クライアント実物を動かす検査**（`web/tools/route_probe.mjs`）と、
**あり得ない値を見張る不変条件**を入れた:
